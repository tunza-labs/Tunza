Purpose

This plan answers two questions. First, how Tunza should build its model: which base model, what the model actually does inside the product, what data it trains on, and when it is allowed to train. Second, how to get full use out of the rented GPU, meaning each run is efficient and the card is busy most of the day. The second part also produces the utilization record that the buy-or-rent decision needs (Ben's bar is 2 to 4 weeks above 50 to 70 percent).

Problem

A LoRA run is already reporting to the live board, but the repo still has no training code, no data pipeline, no model choice on record, and no hardware receipt. Six facts make "just train it" unsafe or wasteful:

  1. The card is unverified. "5090" is a remote desktop label. An RTX 5090 has 32 GB of GPU memory. A 96 GB Blackwell card is the RTX PRO 6000. The two cards call for different plans: the PRO 6000 has 3x the memory and about 2.4x the dense BF16 compute (about 504 vs 210 TFLOPS). "96 GB" may also be the PC's system RAM, which does not help GPU training much. nvidia-smi has never been run.
  2. The box runs Windows. Blackwell (sm_120) training works best on Linux. Native Windows works through Unsloth's Windows path, but bitsandbytes 4-bit on Windows Blackwell is not confirmed. WSL2 has an open bug: on an RTX PRO 6000 the CUDA context took about 16 GiB, versus 1 to 2 GiB on native Linux (microsoft/WSL#40401).
  3. Training is closed on paper. evals/BUILD-PROMPT.md section 7 keeps the fine-tune slot blocked until five things are written by people: Y, the product, a clinician-signed protocol pack and ceiling, a data-rights note, and a sealed held-out gold set.
  4. No measured utilization. The board shows tokens per second but not how busy the GPU is or what fraction of its peak compute is used (MFU). So nobody can tell a slow run from a run starved by a bottleneck.
  5. Swahili is the hard part, not size. AfriMed-QA is English-only, and no public benchmark measures Swahili or code-switched community health worker (CHW) triage. A bigger model does not fix that. Our own en, sw and codeswitch strata do.
  6. The product needs a small model. CHW phones and clinics with poor connectivity favor a 4B to 12B model. A 70B model trained on a few thousand labeled cases would be slower and no safer.

Solution

What the model does. The model reads an encounter (typed or transcribed, in English, Swahili or code-switched) and returns strict JSON with three things: the danger facts it found, a proposed disposition from the contract's six (go_now, get_care_today, monitor_at_home, need_one_more_answer, escalate, abstain), and the one question to ask next. It does not make the final call. lib/clinical/reconcile.ts applies the decide() floor: a lower proposal is rewritten up, and a downgrade never ships. The model's value is reading messy bilingual input that keyword rules miss and asking the right next question. It is not there to overrule the floor.

How it is built. Start from a strong open base model and train one LoRA adapter with supervised fine-tuning, as the 2026-09-10 plan set. Untuned candidates are first compared on our own two scorecards. The clinical fine-tune runs only after the five opening criteria exist. Until then the GPU does engineering work: the stack, the throughput tuning, the untuned bake-off, and pipeline shakedown runs on public non-clinical data whose weights are thrown away.

How the GPU stays full. Two layers. Within a run: BF16 LoRA when the model fits (no 4-bit dequantize cost), padding-free packing with FlashAttention, the largest micro-batch that fits in about 90 percent of memory, fused kernels (Unsloth or Liger) including chunked cross-entropy, a pre-tokenized dataset, and no per-step GPU syncs for logging. Each lever is measured by MFU. Across the day: a job queue that runs training, then evals, then the next sweep config without gaps, plus a utilization logger whose daily busy percentage feeds the rent-or-buy decision.

[] Phase 0: Hardware receipt and inventory of the live run

Prove which card is in the box and what the run on the board is. Every number later in this plan depends on the answer. Run this on the box, in PowerShell, by a human or an agent the human has explicitly sent there.

0.1. Hardware receipt

  • [] Run nvidia-smi and nvidia-smi -q -d MEMORY,CLOCK,POWER,PERFORMANCE. Save both outputs to vault/sessions/ without the host name or IP.
  • [] Record the card name, total memory, driver, CUDA version, power limit, and system RAM (Get-CimInstance Win32_ComputerSystem).
  • [] Branch: 32 GB (RTX 5090) uses the 32 GB column of the model table in Notes. About 96 GB (RTX PRO 6000) uses the 96 GB column. Anything else: stop and report the real chip, per BUILD-PROMPT.md rule 2.

0.2. Inventory the run already on the board

  • [] Write into vault/training.md: the script path, base model, dataset and its source, LoRA rank and targets, learning rate, sequence length, batch size, 4-bit or BF16, and whether it runs in native Windows, WSL2 or Docker.
  • [] If its dataset is clinical, or of unknown origin, label the run shakedown in the vault and do not promote its adapter. Stopping it is Evan's call.

0.3. Testing Strategy

[] Phase 1: A pinned Blackwell training stack on the box

Get one reproducible stack that sees sm_120, uses FlashAttention, and leaves the most GPU memory free. Order of preference: (1) native Windows with Unsloth's documented Windows install, if check_gpu.py passes; (2) the Unsloth Docker image on WSL2; (3) ask the provider for a Linux image. On a 96 GB card, measure the WSL2 context overhead before choosing WSL2, because of the 16 GiB bug.

1.1. Install and pin

  • [] Create a Python 3.11 or 3.12 venv in training/.venv. Install PyTorch built for CUDA 12.8 or newer, then Unsloth, then flash-attn 2.8.1 or newer.
  • [] Freeze the exact versions into training/env/requirements-blackwell.txt.
  • [] Set Windows power plan to High performance, turn on hardware-accelerated GPU scheduling, and close GPU-heavy apps. The Chrome Remote Desktop session also uses the GPU for encoding, so disconnect during long runs.

1.2. Hardware receipt script

  • [] Write training/env/check_gpu.py: print the arch list (must include sm_120), free and total memory after creating the CUDA context, an 8192x8192 BF16 matmul loop reporting achieved TFLOPS, a flash-attn forward and backward on a toy tensor, and a bitsandbytes 4-bit linear forward.
  • [] If bitsandbytes fails, mark 4-bit as unavailable and use BF16 or 8-bit only. Do not chase a 4-bit build on this phase's clock.

1.3. Testing Strategy

The script is the test. Edge cases: a PyTorch wheel without sm_120 (falls back with a "no kernel image" error), flash-attn installed but silently replaced by SDPA, and WSL2 hiding overhead from mem_get_info. Compare free memory against nvidia-smi, not only against PyTorch.

  • [] python training/env/check_gpu.py — Exit 0 with sm_120 listed, flash-attn OK, and matmul at or above 70 percent of the card's dense BF16 peak.
  • [] python -c "import torch; print(torch.__version__, torch.version.cuda, torch.cuda.get_device_name())" — Proves the pinned build is the one in use.
🔁 Do not exit this phase until every box above is checked. If any command fails, fix the cause and re-run — loop until all pass.

[] Phase 2: Measure utilization (board fields, MFU, daily busy percentage)

You cannot fill a GPU you cannot see. Add the missing measurements to the telemetry the board already reads, and start the all-day logger.

2.1. Telemetry fields

  • [] In training/telemetry.py, keep every field the board reads (step, loss, lr, grad_norm, lora_B_norm, tok_per_s, tokens_seen, examples_seen, gpu_mem_gb, elapsed_s) and add gpu_util, power_w, sm_clock_mhz, throttle, mfu, data_wait_ms.
  • [] Compute MFU as tok_per_s * 4 * N_params / peak_flops. A frozen base model does a forward pass and an activation-gradient pass, about 4N FLOPs per token. Recompute from gradient checkpointing is not counted as useful work. Peak is 209.5e12 for the 5090 and 503.8e12 for the PRO 6000, BF16 dense, unless Phase 1's microbenchmark shows a different real ceiling.
  • [] Read GPU counters through NVML (pynvml) in a background thread every 10 s. Reduce loss on the GPU and copy to CPU only at log steps.
  • [] Ask the board owner to add gpu_util and mfu charts. Old runs without these fields must still render.

2.2. All-day logger

  • [] training/gpu_util_logger.ps1 runs nvidia-smi --query-gpu=timestamp,utilization.gpu,memory.used,power.draw,clocks.sm,temperature.gpu,clocks_throttle_reasons.active --format=csv,noheader -l 10 into runs/util/YYYY-MM-DD.csv, registered as a Windows scheduled task at logon.
  • [] A daily summary gives busy percentage (samples with util above 10 percent, divided by all samples) and average MFU while busy. These go into vault/training.md weekly, which is the evidence Ben's buy bar asks for.

2.3. Testing Strategy

Unit-test the MFU math and the JSONL schema with pytest. Then check against a known case: the Exxact benchmark ran Llama 3.1 8B LoRA on an RTX PRO 6000 at 4,962 tok/s, which this formula puts at about 31.5 percent MFU. The logger is checked by letting it run for 5 minutes during a training job.

  • [] python -m pytest training/tests/test_telemetry.py -q — MFU math, schema compatible with the board, no field removed.
  • [] Get-Content runs/util/$(Get-Date -Format yyyy-MM-dd).csv -Tail 5 — Logger is writing live rows.
🔁 Do not exit this phase until every box above is checked. If any command fails, fix the cause and re-run — loop until all pass.

[] Phase 3: Throughput tuning, one lever at a time

Benchmark on a public non-clinical dataset (for example a general Swahili-English instruction set with a license that allows training), 200 steps per config, same base model as the Phase 4 front-runner. Change one lever per row and keep it only if tok/s goes up and loss at step 200 holds.

3.1. The matrix (in order)

  • [] Baseline: BF16, padded batches, micro-batch 1, gradient checkpointing on. Record tok/s, MFU, peak memory, data_wait_ms.
  • [] Precision: BF16 base instead of 4-bit when the model fits. 4-bit dequantize costs throughput. Use QLoRA only to fit a model that would not otherwise fit.
  • [] Padding-free packing with FlashAttention 2. Pick max_seq_length from the real length histogram (around the 99th percentile), not a round number.
  • [] Micro-batch: double until peak memory reaches about 90 percent, then lower gradient accumulation to keep the same effective batch.
  • [] Gradient checkpointing: off if it fits. Otherwise use Unsloth's offloaded checkpointing, which uses system RAM. Here 96 GB of RAM does help.
  • [] Fused kernels: Unsloth kernels or Liger (RMSNorm, RoPE, SwiGLU, fused linear cross-entropy). Chunked cross-entropy matters most for big vocabularies: Gemma's 262k vocab at 2,048 tokens is about 2 GB of FP32 logits per sequence.
  • [] Input pipeline: pre-tokenize to Arrow once, use pin_memory, and set worker count so data_wait_ms is near 0. On Windows, worker processes spawn slowly, so use persistent_workers=True.
  • [] Logging: no .item(), print of tensors, or torch.cuda.synchronize() per step.
  • [] torch.compile last, and only if it is stable with PEFT on this stack.
  • [] Thermals: if throttle is non-zero for long periods, fix airflow or the power limit before changing any code.

3.2. Targets

  • [] GPU util above 95 percent during steps, data_wait_ms under 2 percent of step time, and MFU at or above 35 percent (stretch goal 45 percent). For a 9B model on a 5090, 35 percent MFU is about 2,000 tok/s.
  • [] Write the winning settings into training/configs/*.yaml and the table of results into vault/training.md.

3.3. Testing Strategy

Each config is one queued job with a fixed seed. Losses at step 200 must agree within noise across levers. A lever that changes the loss curve is a bug, not a speedup (for example, packing without attention masks leaks across examples). Run each row twice and keep the median.

  • [] python training/bench/throughput_matrix.py --model <front-runner> --steps 200 --repeat 2 — Produces the results table with tok/s, MFU, memory, and loss@200 per lever.
  • [] python training/bench/throughput_matrix.py --check-loss-parity — Fails if any kept lever moves loss@200 by more than 2 percent.
🔁 Do not exit this phase until every box above is checked. If any command fails, fix the cause and re-run — loop until all pass.

[] Phase 4: Keep the GPU busy all day with a job queue

A fast run that leaves the card idle overnight still wastes money. One runner process owns the GPU and pulls jobs in priority order: training, then evaluating that adapter, then the next sweep config, then the bake-off backlog.

4.1. Runner

  • [] training/queue/runner.py: watch queue/jobs/, run one job at a time, move it to queue/done/ or queue/failed/ with its log, and call gate.py before any job tagged clinical.
  • [] Resume from the latest checkpoint after a crash or a Windows Update reboot. Pause Windows Update during long runs and checkpoint every 30 minutes.
  • [] When the queue is empty, notify Evan once. Do not invent work to look busy.

4.2. Testing Strategy

Test with three tiny jobs (10 steps each) and one deliberately failing job. Kill the runner in the middle of a job and confirm it resumes from the checkpoint.

  • [] python -m pytest training/tests/test_queue.py -q — Ordering, failure isolation, resume, and the gate refusing a clinical job.
  • [] Daily busy percentage from the Phase 2 logger is above 70 percent on days with queued work.
🔁 Do not exit this phase until every box above is checked. If any command fails, fix the cause and re-run — loop until all pass.

[] Phase 5: Untuned base-model bake-off on our own scorecards

Pick the base model with evidence before any clinical data exists. This fills the Untuned candidate slot in the eval harness. It depends on the eval harness from evals/BUILD-PROMPT.md being built. Reports carry engineering_regression_only, because the gold is still synthetic.

5.1. Candidates

  • [] Check each model card for license, real sizes, context length, and language list before the run. The Qwen 3.5 and Gemma 4 sizes come from secondary sources.
  • [] On 32 GB: MedGemma 1.5 4B (medical-tuned, small), Qwen 3.5 9B, Gemma 4 12B, plus decide() as the floor.
  • [] On 96 GB, add: MedGemma 27B (text), Gemma 4 31B, Qwen 3.5 27B.

5.2. Measures (never averaged)

  • [] Downgrade-against-floor count before reconciliation. It shows how often the floor has to save the model.
  • [] Scorecard A under-triage rate with its Clopper-Pearson upper bound, separately for en, sw and codeswitch. The clinical pass stays blocked while the ceiling is unset.
  • [] Abstain false-answer rate, JSON validity rate (with grammar-constrained decoding), danger-fact recall, and p95 latency at batch size 1 on this card.
  • [] Swahili quality: a native speaker rates 50 of the model's follow-up questions in Swahili for fluency and clarity. This is the one human step in this phase.

5.3. Testing Strategy

Same locked rows, same prompt, same decoding settings, and temperature 0 for every candidate. Same-model self-grading is forbidden (wave1-contract). The harness compares against the frozen expected labels, not a model judge.

  • [] python training/eval_candidate.py --model <id> --rows evals/manifest.json --out runs/bakeoff/<id>.jsonl — One JSONL file per candidate, with hashes matching the manifest.
  • [] npx vitest run tests/eval-baseline.test.ts (on the Mac, focused) — Frozen baseline hash still matches, so no fixture changed.

[] Phase 7: Gated SFT, then shadow mode

This runs only after gate.py --check prints open. It trains one LoRA adapter on the front-runner from Phase 5 and runs it in shadow mode beside decide(). Shadow mode changes no screen, stored decision or referral.

7.1. Recipe (starting point; tuned only on the train split)

method: LoRA (BF16 base if it fits; QLoRA 4-bit only to fit)
targets: all linear projections (q,k,v,o,gate,up,down)
rank: 16   alpha: 32   dropout: 0
loss: assistant tokens only (JSON answer), prompt masked
lr: 1e-4, cosine, warmup 3%     grad_clip: 1.0     weight_decay: 0
effective batch: 32 sequences   epochs: 2 (stop on facility/time-held-out val)
max_seq_length: p99 of real lengths, padding-free packing
seeds: 3 (report the spread, not the best one)
output: JSON constrained to the contract-six enum + danger facts + next question
  • [] Validation split is by facility and time, never random rows (BUILD-PROMPT section 5).
  • [] Score every seed with both scorecards. Promotion means shadow only, and only if the downgrade-against-floor count is 0 after reconciliation and Scorecard A is within the signed ceiling in every language stratum.
  • [] Shadow mode logs model and floor disagreements for clinician review. Those reviews become the next round's labels.

7.2. Testing Strategy

The sealed gold set is opened once per candidate, never during tuning. The gold hash is checked before scoring. A rules card that ties the model on Scorecard B means the rules are kept (BUILD-PROMPT).

  • [] python training/gate.py --check — Prints open before the job starts. Otherwise this phase stays [].
  • [] python training/eval_candidate.py --adapter runs/<tag>/adapter --rows sealed_gold --verify-hash — Gold hash matches and both scorecards are written separately.

The recommended default is the best of the 4B to 12B group in Phase 5. Data size decides this, not GPU size: with a few thousand labeled cases, a 9B adapter will usually match a 31B one on a narrow task, and it runs much cheaper in the field. The 96 GB card is better spent on faster sweeps and 3 seeds than on a bigger base model.

N2. Throughput math to sanity-check the board

useful FLOPs per token (frozen base, LoRA)  ≈ 4 × N
MFU = tok_per_s × 4 × N / peak_bf16_dense

5090      peak ≈ 209.5 TFLOPS → 9B at 35% MFU ≈ 2,040 tok/s
PRO 6000  peak ≈ 503.8 TFLOPS → 9B at 35% MFU ≈ 4,900 tok/s
Reference: Exxact, Llama 3.1 8B LoRA, PRO 6000, HF Transformers,
           seq 512, batch 2 → 4,962 tok/s ≈ 31.5% MFU

If the board shows a much lower tok/s for the model size, look at data_wait_ms, padding, micro-batch 1, 4-bit dequantize, and per-step syncs, in that order.

N3. Open decisions (only Evan and the clinician can close these)

  • D1. Product: household_advice, chp_worklist or both_separate. This changes which scorecard gates promotion and what the model outputs (a disposition, or a rank score under capacity K).
  • D2. Y, the label column.
  • D3. The clinician, protocol pack and ceiling.
  • D4. Data source and data-rights note. Being connected to eCHIS is not that note.
  • D5. Whether training code lives in this public repo (this plan's default, with data and weights ignored by git) or in a private repo.

N4. Risks

  • R1. The live run trains on unclear data. Phase 0.2 labels it shakedown until proven otherwise.
  • R2. WSL2 on Blackwell hides about 16 GiB of overhead from PyTorch. Measure with nvidia-smi.
  • R3. bitsandbytes 4-bit is unconfirmed on Windows sm_120. The plan prefers BF16 and treats 4-bit as optional.
  • R4. A Kenyan LLM decision-support study (cited secondhand) reported 7.8 percent of AI recommendations as harmful. The floor-wins reconciler and shadow-first rollout exist for this reason.
  • R5. Rental PCs reboot. Checkpoints every 30 minutes and queue resume cover it.

N5. Rejected approaches

  • From-scratch pretraining and 70B models: already rejected on 2026-09-10, and pointless with this data size.
  • Training on engineering fixtures, or on IMCI and ETAT numbers typed in by an agent: this fakes a clinical approval (BUILD-PROMPT section 7).
